# LLM training — llama2.c on ESP32-S3 N16R8

Goal: train a tiny llama2.c-style transformer and run it fully on-device on
the ESP32-S3 N16R8 (16MB flash / 8MB PSRAM), as an offline replacement for a
cloud-LLM conversation engine. See the project plan for full context and the
phased roadmap; this directory covers the training side (Phases 1, 3, 4).

## What's here

```
vendor/llama2c/     Karpathy's llama2.c, vendored as-is (train.py, export.py,
                     run.c/runq.c C inference, tokenizer tooling)
scripts/             our own scripts, not part of upstream llama2.c
  generate_corpus.py   Phase 1 ONLY: synthetic smoke-test corpus (see below)
  prepare_data.py       trains a custom sentencepiece tokenizer + pretokenizes
                         a corpus into the shard layout train.py expects
data/                generated by the scripts above — not committed (see .gitignore)
out/                 training checkpoints — not committed
venv/                Python virtualenv — not committed
```

## Phase 1 status: pipeline validated (2026-09-24)

The goal of Phase 1 was to prove the full loop — tokenizer training → model
pretraining → int8 export/quantization → C inference — works end-to-end
*before* touching ESP32 hardware. That's done. What actually happened,
and an important caveat:

**Network constraint hit:** the plan's original Phase 1 called for
downloading Karpathy's pretrained `stories260K` checkpoint and the
TinyStories dataset. Both are hosted on `huggingface.co`, which this
environment's network policy blocks (GitHub is reachable, HuggingFace is
not). **On a normal laptop this restriction won't exist** — downloading the
real `stories260K` checkpoint directly (see `vendor/llama2c/doc/stories260K.md`)
is worth doing there for comparison.

**What we did instead:** `scripts/generate_corpus.py` writes a small
self-authored synthetic corpus (1200 template-generated sentences, no
network needed), and `scripts/prepare_data.py` trains a custom 512-token
sentencepiece tokenizer on it and pretokenizes it into the shard `.bin`
layout `train.py` expects. We then trained the exact `stories260K`
architecture (`dim=64, n_layers=5, n_heads=8, n_kv_heads=4`, 259K params) for
only 150 iterations (~10 seconds on this machine's CPU) — enough to confirm
training loss drops (6.26 → 2.08) and every stage runs without error, not
enough to produce a good model.

**Result:** the full pipeline runs cleanly:
`train.py` → checkpoint (`out/smoke/ckpt.pt`, `model.bin`) →
`export.py --version 2` (int8 quantized, **278KB**, right in line with the
real `stories260K`'s "a few hundred KB" size) → `runq` (C inference, no
Python) → generates tokens successfully. Text quality is poor/incoherent, as
expected from a model trained for 150 steps on a toy corpus — **this run was
about proving the plumbing, not producing a usable model.** Getting
actually-good output (like the real `stories260K` demo) needs many more
iterations on a much larger corpus, which is exactly what Phase 3/4 (the
real EmoBot personality dataset, trained for far longer) are for.

### Reproducing

```
cd llm-training
python3 -m venv venv && source venv/bin/activate
pip install torch numpy sentencepiece requests tqdm

python scripts/generate_corpus.py
python scripts/prepare_data.py

ln -s ../../data vendor/llama2c/data   # train.py expects ./data relative to its own dir
cd vendor/llama2c
python train.py --out_dir=../out/smoke --vocab_source=custom --vocab_size=512 \
  --dim=64 --n_layers=5 --n_heads=8 --n_kv_heads=4 --multiple_of=4 \
  --max_seq_len=128 --batch_size=8 --max_iters=150 --warmup_iters=20 \
  --eval_interval=50 --eval_iters=10 --device=cpu --dtype=float32 --compile=False

python export.py ../out/smoke/model_q8.bin --version 2 --checkpoint ../out/smoke/ckpt.pt

make run runq   # or: gcc -O3 -o run run.c -lm && gcc -O3 -o runq runq.c -lm
./runq ../out/smoke/model_q8.bin -z data/tok512.bin -t 0.0 -n 80
```

## Next steps (Phase 2+)

- **Phase 2** (needs the physical N16R8 board): port `run.c`/`runq.c` to
  ESP-IDF/PlatformIO — flash-mmap the quantized weights from a raw partition
  instead of `fread`, put KV-cache/activations in PSRAM, and reproduce this
  same smoke-test generation on-device to get a real tokens/sec number.
- **Phase 3** (needs the user): replace `generate_corpus.py`'s synthetic
  template text with a real hand-curated EmoBot personality dataset —
  short, in-character lines per trigger category (mood-sad, mood-happy,
  life-event, greeting, etc.), a few thousand examples.
- **Phase 4**: pick a model size between `stories260K` and `stories15M` that
  fits the ~4-8MB int8 flash budget, train it properly (many more iterations
  than this smoke test) on the curated dataset, and verify output quality
  qualitatively before moving to hardware integration.
